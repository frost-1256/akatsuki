# Akatsuki マイルストーン M1（表示専用ドライバ）スコープ

2026-11-06 作成。位置づけ: 構想文書（`adreno-oss-driver-concept.md`、spacewar 側 goal files に所在）の下で、最初のマイルストーン M1 の範囲を具体化する作業文書。実装計画そのものではなく、「何を作り、何を作らないか」「何が既に分かっていて、何が未決か」を固定する。

着手の経緯: 本線（公式ドライバ qcdxkm7325 の正常化）は表示の詰めと凍結で長期停滞しており、2026-11-06 にユーザー判断で本スコープの作成に着手した。構想文書の始動条件（GPU 周りの解析が進んでから）は、表示レジスタ設定の仮説空間が閉じ、残課題がフレーミングとプラットフォーム層に特定されたことで、実質的に満たされたとみなす。

## M1 の定義

**M1 = 自作の表示専用カーネルドライバで、spacewar の内蔵パネルに Windows の画面を正しく表示する。**

- 対象機: Nothing Phone (1)「spacewar」（SM7325、表示パネル Visionox RM692E5、1080×2400）
- 対象 OS: Windows 11 22H2 ARM64（本線と同一環境、テスト署名運用）
- ドライバ種別: Windows Display Driver Model の表示専用（display-only）ドライバ。レンダリング系の Device Driver Interface は実装しない。画面の合成は OS 側のソフトウェア描画に任せ、本ドライバはモード設定とスキャンアウト、Present の受け取りだけを担う
- 表示対象は内蔵パネルのみ。外部出力は扱わない

### ゴール

- 自作ドライバ経由で、テストパターンまたはフレームバッファの内容が**正しい絵**としてパネルに出る
- 最終的には Windows デスクトップが表示され、手動有効化セッションの中で安定して使える（本線の安全規則どおり、ブート時無効が既定）

### 非ゴール

- 3D レンダリング、動画再生支援、複数画面、色管理の高度な機能（M2 以降）
- 公式ドライバ qcdxkm との共存（同じ表示ハードウェアに二重にバインドしない。実験時は公式側を無効化する）
- 署名の正式化、配布形態（構想段階のまま保留）

## 設計入力（本線の解析資産から確定していること）

M1 はコールドスタートではない。表示まわりは本線の GX 系調査で以下まで仕様化されている。

- **DSC（Display Stream Compression）パラメータは完全一致セットが確定**: DSC 1.1、スライス 540×20、色深度 10、ピクセルあたりビット数 8、Picture Parameter Set の全値が Linux 側デバイスツリーとバイト単位で一致することまで照合済み。「レジスタ設定の線は閉じた」が結論で、残っていたのはフレーミング、順序、タイミング側
- **パネルの初期化シーケンス**: パネル XML のタグ表（完全一致照合、未知タグは無視）と、初期化が最初の失敗パケットで打ち切られる仕様、送信すべきデータ型と長さの表まで解析済み。メインラインの同パネルドライバの送信順序（表示オン完了後に PPS、続いて圧縮モード）も採取済み
- **メインライン動作状態のレジスタ採取**: 正常表示しているメインライン環境からの表示ブロック実値が参照として保存されている
- **DSI エラーの知見**: ハイスピードレーンの underflow ビット群（FIFO_STATUS 0x88880000）は公式ドライバでは分類もクリアもされない。自作側では最初から読み取りとクリアを設計に入れる
- **未確定の値**: DSI ハイスピード timer の値（Windows 0x0004EA60 と downstream 0x0003FD08 の相違、未試行）。M1 では両値を試せる形で定数化する

## 設計規則（本線の事故から得た、最初から守ること）

- **電源は Platform Extension Plug-in（PEP）のデバイス電源モデルへ正規登録する**。レールをモデルの外から直接叩く（過去に SoC のクリティカル障害を起こした方法）ことはしない。モデルに登録されていない電力要求は他のデバイス起動時の再計算で落とされる、というタッチ電源の教訓をそのまま適用する
- **SMMU のグローバル設定では DVM 参加を切る**。Linux の arm-smmu は sCR0 の PTM ビット（bit 12）を立てて「Disable TLB broadcasting」としている一方、Qualcomm の Windows SMMU ドライバ qcsmmu は bit 12 を明示的にクリアしていることが 2026-11-06 に静的に判明した。これは本線の 0x101 凍結（ブロードキャスト TLB 無効化の相互ランデブー）の最有力機構である。自作ドライバが触る SMMU コンテキストでは、最初から PTM=1 を設計値とする
- **実験の安全規則は本線と同一**: グラフィックス系はブート時無効を既定とし、有効化は短く、終了後は無効化と ConfigFlags の読み戻し確認までをひと続きとする
- **失敗しても戻れる段階で刻む**。各段階は「前段に戻れる」ことを完了条件に含める（ドライバ差し替えは gadget 経由、DriverStore のライブ上書きは禁止、という既存手順を踏襲）

## 段階（M1 内部）

| 段 | 内容 | 完了の目安 |
|---|---|---|
| M1a | ドライバ骨格。表示専用ドライバとして列挙され、モード（1080×2400）を提示し、真っ黒な画面のまま安定する。Present は受け取るが表示はまだ出さない | 有効化セッションを通して凍結なし、無効化と復帰が正常。読み戻しで状態確認できること |
| M1b | パネル点灯。DSI ホストとパネル初期化シーケンスを実装し、表示ブロック内蔵のテストパターン生成で最初の正しい絵を出す | テストパターンが期待どおりの幾何で表示される（ノイズの幾何との対比で判定できる形で記録する） |
| M1c | スキャンアウト。線形フレームバッファを表示パイプラインへ流し、DSC 経路でパネルに正しく届く | 単色、グラデーション、格子など判別可能なパターンが全て正しく出る。DSC オフ経路の可否もここで確定する |
| M1d | Windows デスクトップ。Present 経路を生かし、OS の画面がそのまま表示される | デスクトップ操作が目視で正常。セッション中の安定性と、終了手順の確実さを確認 |

順序の根拠: M1b のテストパターンは本線の表示ラダーの3段目（テストパターン注入）と同一の切り分けであり、ホスト側のフレーム生成を介さずに「パイプラインとパネルだけ」の正しさを先に確定できる。

## 流用資産の棚卸し

- GX 系レポート・ブリーフ群（約270ファイル）: `~/workspace/silicium/opus-session/`。表示レジスタ、DSC、パネル XML、初期化打ち切り仕様、凍結解析の仕様化の蓄積
- DscProbe（読み取り専用計測ドライバ）: `~/workspace/silicium/winboot/dscprobe/DscProbe.c`。M1 の各段で「書いた値が実際に効いているか」の読み戻し検証に使う。本線で不足していた読み出し集合（付録Aのレジスタ群）の追加先でもある
- メインライン採取データ: 正常表示状態の表示ブロック実値（参照値）
- GX74（凍結計測）: プロセッサごとの自己記録リング。自作ドライバの立ち上げで同種の停止が起きた場合の切り分けに流用する
- spacewar-woa リポジトリ: `~/workspace/spacewar-woa/`。導入手順、バイナリパッチ仕様、表示調査の公開記録。M0（仕様の統合）の下敷き
- ビルド・署名基盤: EWDK の ARM64 ビルド手順、spacewar テスト証明書による署名、gadget 経由の配置と照合の手順（いずれも本線で実績あり）
- DSDT v24（run70 系譜）: GPU0 ノードと依存関係の現状。2026-11-06 に PILC／TREE の Started が確認され、_DEP 復帰条件は満たされている（復帰自体は未実施）

## 未決事項（M1a に入る前に決めるもの）

**【2026-11-07 決定済み】** 以下の 5 点は全て `AKATSUKI_M1_DECISIONS.md` で決定として固定した。要約: (1) GPU0 流用（HID 差し替え）、(2) SMMU 変換経由の通常メモリ（PTM=1）、(3) DSC オンを正、(4) KMDOD 系、(5) PoFx 正規登録＋ PEP0 側 COMPONENT エントリ。

1. **バインド先の ACPI ノード**: 既存の GPU0 を自作ドライバに割り当てるか、表示ブロック専用の新ノードを DSDT に切るか。前者は公式ドライバとの排他が単純だが、GPU コア側の依存（サブシステム起動）まで引き受ける可能性がある
2. **フレームバッファの置き場所**: 連続メモリの切り出し（本線の凍結震源だった経路に近い）か、SMMU 変換経由の通常メモリか。PTM 規則と合わせて決める
3. **圧縮の初期値**: DSC オンを正とする（パラメータは確定済み）か、無圧縮の受け入れ可否を先に M1b で測るか。パネル側の無圧縮受信は本線でも未証明のまま
4. **表示専用モデルの世代**: Windows 11 22H2 で使える表示専用ドライバの Device Driver Interface セットの確定（WDK サンプルの Kernel Mode Display-Only Driver 系を土台にするか含む）
5. **クロックと電源の要求経路**: 表示ブロックのクロック投票とレール要求を、PEP モデル経由でどの形で出すか（qcpep の COMPONENT 入りエントリの知見が効く可能性がある）

## リスク

- **凍結の再発**: 自作ドライバでも、サブシステム起動や SMMU 操作が同種の相互ランデブーを引く可能性がある。緩和は設計規則（PTM、電源登録）と、GX74 の流用による早期切り分け
- **カーネルドライバの失敗はブルースクリーン**: 復旧は gadget とオフライン確認が前提。段階を刻み、各段でロールバック可能に保つ
- **パネル仕様の非公開性**: RM692E5 の公開データシートは存在しない。初期化と圧縮の詳細はメインライン実装と本線の観測が根拠であり、最後は実機で決める範囲が残る
- **規模**: 表示だけでも月単位というのが本線側の見積もり感触。M1 は「最初の正しい絵」までの距離を測る段階であり、完成品の見積もりは M1b 終了時点で初めて出せる

## 本線との関係

- M1 の達成は、本線のゴール「GPU を使って少しでも正常に描画する」と同じ到達点である。どちらが先に着いても、もう一方への入力になる（本線の詰まりどころが土台の問題なら自作側でも再現し、自作側で動けば公式側の切り分け材料になる）
- 公式ドライバ正常化の線は本スコープでは止めない。GX74 の Q2（実機計測）や PTM 追跡などの残件は、それぞれ独立に再開できる状態で保持する
