# Akatsuki M1 実装計画

2026-11-07 作成。前提文書: `AKATSUKI_M1_SCOPE.md`（範囲と設計規則）、`AKATSUKI_M1_DECISIONS.md`（未決 5 点の決定）、`AKATSUKI_M1_ACPI_NODE.md`（GPU0 の実測詳細）。本計画は M1a（骨格）を主対象に、M1b〜M1d への接続までを作業パッケージに分解する。各パッケージには根拠となる既存資産を明記する。

## 全体方針

- 土台は WDK サンプルの KMDOD（決定 4）。自前で書くのは「spacewar の表示ブロック固有」の部分だけに絞り、VidPn・子列挙・電源状態などの定型はサンプルの実績ある形を残す
- 段階ごとに「前段へ戻れる」ことを完了条件に含める（スコープの設計規則）。配置は gadget 経由＋ハッシュ照合、DriverStore のライブ上書き禁止、ブート時無効が既定、有効化セッションの後は ConfigFlags 読み戻し、という本線の手順をそのまま使う
- **再インストール耐性を要件に入れる**。2026-11-07 の事故（公式ドライバが HKLM\SOFTWARE の設定欠落で開始不能になった）は、「ドライバが依存するプラットフォーム側設定が、ドライバの外に散らばっていると黙って壊れる」ことの実証だった。Epinephrine が依存するプラットフォーム側設定（DSDT 差分、PEP0 エントリ、レジストリ値）は全て **プラットフォーム設定マニフェスト**として一覧化し、リポジトリで版管理する。再インストール時はマニフェストの再適用手順だけで復旧できる状態を保つ

## 成果物の構成

```
epinephrine/
  src/            KMDOD 土台＋自前コード（表示ブロック制御、EDID 合成、電源登録）
  inf/            Epinephrine.inf（Display クラス、自作 HID にマッチ）
  platform/
    MANIFEST.md   プラットフォーム設定マニフェスト（下記 WP3/WP7 の成果物）
    dsdt/         GPU0 HID 差し替えの DSL 差分とビルド済み AML
    pep/          PEP0 Resources への自デバイスエントリ（書式確定後に格納）
  tools/          読み戻し確認用スクリプト類（DscProbe 連携を含む）
```

- 自作 HID は **`AKAT0001`** とする（ACPI 文字列 ID、INF は `ACPI\AKAT0001` にマッチ）。GPU0 の `_HID` を `QCOM0A36` から差し替えることで公式ドライバとの排他を構造的に担保する（決定 1）

## 作業パッケージ

### WP1: DSDT 差分（GPU0 HID 差し替え）

- ベースは本番系譜 **v24（run70）**。現在の repo HEAD は v27（テスト用 PCFG 入り）なので、Akatsuki 用ブランチは v24 から切る。変更は GPU0 の `_HID` 1 点のみ。`_DEP`（8 件: MMU0, MMU1, IMM0, IMM1, PEP0, PMIC, RPEN, SCM0）、`_CRS`、`_ROM` は無変更
- コンパイルは出荷用 iasl 20260930。検証は「逆コンパイル差分が HID とヘッダ（長さ・チェックサム）だけ」を必須ゲートにする（v31/v32 で確立した検証手順の流用）
- ロールバック用に無変更 v24 イメージを常に手元に置く。`_DEP` は列挙ゲートなので、HID 差し替え後に自ドライバが開始失敗しても GPU0 自体は列挙される（バインド先が自ドライバになるだけ）ことが、公式復帰の容易さの根拠
- 根拠資産: `AKATSUKI_M1_ACPI_NODE.md` の GPU0 実測（`_CRS` 14 リソースと RESI 名称対応表）

### WP2: ドライバ骨格（M1a 本体）

- KMDOD サンプル（microsoft/Windows-driver-samples の video/KMDOD）を取り込み、ARM64・テスト署名でビルドが通る状態をまず作る（EWDK 手順は本線で実績あり）
- StartDevice では `_CRS` のリソースを受け取る。表示系（MDP_REGS 0x0AE00000・2MB 窓、DP_PHY_REGS、VSYNC_INTERRUPT=IRQ 0x73、DSI_PANEL_RESET=GPIO 44）だけをマップし、GFX／VIDEO 系（GFX_REGS、VIDEO_REGS 等）は**要求も初期化もしない**（決定 1 の注意点）。リソースの対応付けは RESI の名前ベースで行い、順序依存にしない（未検証点だった `_CRS`↔RESI 順序への依存を設計で回避する）
- EDID: 子デバイス（MON0）の記述子として返す EDID は、PCFG（`_ROM`）の EDID Configuration グループから合成する。公式ドライバが同方式で合成していること、グループ欠落で不正 EDID になり dxgkrnl がアダプタを外すことは本線で実証済み（GX14）。**照合用の黄金値**として、現環境で qcdxkm がレジストリに書いた 128 バイト EDID を採取しておき、合成結果とバイト比較する（採取は実機側の読み取り作業）
- モード提示は 1080×2400 を正とし、リフレッシュは実機の提示実績（現環境で 60Hz が提示されている）から始める。Present は M1a では受け取って捨てる（黒のまま安定が完了条件）
- 割り込み: VSYNC（IRQ 0x73）の登録とカウント読み出しだけ実装し、M1c の Present ペーシングに備える
- 診断 Ioctl: レジスタ読み戻しと内部状態の取得口を最初から持つ。DscProbe（読み取り専用計測ドライバ、本線資産）と併用し、「書いた値が効いているか」を外部からも検証できる形にする

### WP3: 電源（PoFx 登録と PEP0 エントリ）

- 順序が肝心で、**まず実機で PEP0 の `Device Parameters\Resources` の現行エントリを読む**（書式の正本は実物）。特に COMPONENT レコードを持つ既存エントリの形を写す。読み取りはユーザー側作業として切り出す
- ドライバ側は PoFx 登録の骨格を M1a に入れる（コンポーネント定義は表示コア系／DSI 系の 2 つを初期値とし、F 状態とクロック水準の対応は WP6 の実測で詰める）。M1a の完了条件は「D0／D3 遷移で落ちない、PEP の再計算で巻き込まれない」までとし、本格的なクロック投票の実効確認は M1b の点灯とセットで行う
- PEP0 エントリ（自デバイス向け・COMPONENT 入り）は `platform/pep/` に格納し、マニフェストに載せる（決定 5）
- 根拠資産: qcpep RE 決着（2026-10-29、デバイスモデルは PEP0 レジストリが正本、COMPONENT 無しでは投票が消費されない読み）、タッチの電源登録の教訓、生レール叩き事故（2026-10-28）の禁止規則

### WP4: SMMU と フレームバッファ（M1c の先行設計、M1a では調査のみ）

- フレームバッファは通常ページ＋自前 SMMU コンテキストの IOVA（決定 2）。M1a では確保もマッピングもしないが、次を机上と読み取りで潰しておく：
  - 表示ブロックが使う SMMU コンテキストの同定（qcsmmu の RE 資産と、公式スタック動作時のコンテキスト設定の読み戻し）
  - PTM の扱いの正直な整理: PTM は SMMU グローバル設定（sCR0）のビットで、所有者は qcsmmu 側。自ドライバのコンテキスト設定で完結する話ではないため、「自コンテキストで可能な範囲は DVM 非参加寄りに寄せ、グローバル側は本線の PTM 追跡（停止中）の再開判断と連動させる」と計画に明記する。凍結の早期切り分けには GX74 を流用する（スコープの流用資産）
- 根拠資産: qcsmmu 逆アセンブル（sCR0 ビルダ 2 系統とも PTM クリアの静的確認）、凍結解析一式、GX74

### WP5: ビルド・署名・配置のパイプライン

- ビルド: EWDK の ARM64（`BuildEnv\SetupBuildEnv.cmd` を直接 call する既存の教訓どおり）。署名は spacewar テスト証明書
- 配置: gadget 経由のコピー＋ハッシュ照合、サービス登録はオフライン hive 編集の既存手順。**配置と実機操作はユーザー側、コード・仕様・レビューは机上側**という現在の役割分担を計画の前提とする
- コード変更は出荷前レビュー（実装者と別主体）を通す既存規則を適用する

### WP6: M1a 実機試験プロトコル

1. 前提: 本番 v24 イメージと Akatsuki イメージ（WP1）の 2 本を用意。公式ドライバは ConfigFlags=1（無効）を確認してから開始
2. Akatsuki イメージで起動 → Epinephrine を配置 → 有効化セッション（サインイン画面基点の本線作法）
3. 確認項目: デバイスが Started／モード 1080×2400 が提示される／画面が黒のまま安定（数分）／タッチ・Wi-Fi が無事／無効化が正常／ConfigFlags 読み戻し
4. 失敗時: その場で深追いせず、状態（問題コード、イベント、DscProbe 読み戻し）を回収して机上で判定する。ロールバックは v24 イメージ＋公式ドライバ再有効化
5. M1a 完了の定義はスコープどおり: 有効化セッションを通して凍結なし、無効化と復帰が正常、読み戻しで状態確認できること

### WP7: M1b への先行実装（点灯の部品集め）

M1a と並行して机上で進める。実機投入は M1a 完了後。

- パネル初期化シーケンス: パネル XML のタグ表と初期化打ち切り仕様（最初の失敗パケットで打ち切り、後続の 0x11/0x29 と PPS が飛ぶ）は解析済み。実装は「全パケットの型と長さを送信前に検証してから流す」形にし、打ち切りを踏まない構造にする
- DSI ホストと表示ブロックの初期化値は、メインライン正常表示時の採取レジスタを正本とする。未確定の DSI ハイスピード timer は 2 候補（Windows 0x0004EA60／downstream 0x0003FD08）を名前付き定数で差し替え可能にしておく（スコープの設計入力）
- DSC は決定 3 のパラメータと送信順序（表示オン → PPS → 圧縮モード → 28ms）をそのまま実装単位にする
- テストパターンは表示ブロック内蔵生成を使い、幾何が判別できるパターン（色帯・格子）を最初の一枚とする。ノイズ幾何（スライス境界・周期）との対比で判定できる記録方法を先に決める

## 順序と依存

1. WP1（DSDT 差分）と WP2（骨格のビルド通過）は独立に進められる
2. WP3 の読み取りはベースラインが新鮮な今のうちに済ませる（再び環境が変わる前に正本を取る）
3. WP5 のパイプラインは WP2 のビルド通過と同時に立ち上がる
4. WP6（実機）は WP1＋WP2＋WP5 が揃った時点。WP4 と WP7 は M1a と並行する机上作業

## リスクへの対応（スコープからの継続）

- 凍結再発: PTM の整理（WP4）と GX74 の待機。兆候が出たら M1 を止めて本線の凍結線に合流する
- ブルースクリーン: 段階を刻み、各段でロールバック可能に保つ（WP6 の手順）
- パネル仕様の非公開性: メインライン採取値と本線観測が根拠。最後は実機で決める範囲が残ることを前提に、定数は全部「差し替え可能な名前付き定数」として実装する
- プラットフォーム設定の drift: マニフェスト（全体方針）で管理し、環境再構築時はマニフェスト適用から始める
