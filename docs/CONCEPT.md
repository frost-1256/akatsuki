# オープンソース Windows 用 Adreno ドライバ構想

## この文書の位置づけ

これは新規プロジェクトの「構想」文書であり、確定した実装計画ではない。着手順序、担当、期限はまだ決まっていない。

本線は別にある。Nothing Phone (1)「spacewar」（System-on-Chip は SM7325、グラフィックス処理装置は Adreno 642L）上の Windows 11 22H2 で、Qualcomm 公式ドライバ `qcdxkm7325.sys` を正常に動作させる作業が進行中であり、現在の壁は表示の Display Stream Compression（DSC）ノイズと BugCheck 0x101 の凍結である。本構想はそれとは分離した、純粋な好奇心枠の将来構想であり、本線の順序を変えるものではない。

動機はひとつである。Linux の Nouveau のように、権利的に安全な方法で Adreno をリバースエンジニアリングし、オープンソースの Windows 用 Adreno ドライバを作ってみたい、という興味である。時間は度外視する前提で書く。

### 名称

名称は 2 つだけに固定する（2026-11-07、はるの決定で簡素化。旧案のスタック名 Libreno は廃止）。

- 大元のプロジェクト： **Akatsuki Project**
- フリーな Adreno ドライバ本体： **Epinephrine**（アドレナリンの学名）

### 始動条件

本格的に計画を進めるのは、spacewar 本線側の GPU 周りの解析が進んだ段階になってからとする。それまでは本構想は構想として保留し、本線の作業を優先する。

## ゴールと非ゴール

### ゴール

- Windows Display Driver Model（WDDM）向けのオープンソース Adreno ドライバを作る。
- 初号ターゲットは SM7325 / Adreno 642L（A6xx 系）とする。手元の実機で観測でき、本線の知見がそのまま効くためである。
- ユーザーモード側は Vulkan とし、既存の Turnip を再利用する。
- Direct3D は、Vulkan への変換層である DXVK 経由で受ける。

### 非ゴール

- ネイティブな Direct3D ユーザーモードドライバを新規に開発しない。書くべき新規コードは他に集中させる。
- Qualcomm のファームウェア blob を再配布しない。ドライバは、利用者が正規に入手した blob を読み込むだけの形にする。
- 公式ドライバの置き換えを短期に目指さない。本線が公式ドライバの正常化であることと矛盾させない。

## なぜコールドスタートではないか

Nouveau の一番重い工程は、レジスタもシェーダ命令セットも文書がなく、ブラックボックス観測から起こす作業だった。Adreno にはその工程を済ませた先行者がいる。

Mesa の freedreno 系には、少なくとも次の公開資産がある。

- Turnip は Adreno 6xx 向けの Vulkan 1.3 ドライバであり、freedreno の OpenGL ドライバと中核を共有する（Mesa 公式文書）。
- レジスタ定義とコマンドストリーム定義は、XML 形式のレジスタデータベース（rnndb 系の記述）に由来する形で共有されている。
- シェーダコンパイラ ir3 は freedreno と Turnip の共通バックエンドであり、命令セットの知見がコードと文書として公開されている。

つまり「グラフィックス処理装置の言葉が分かる」状態から始められる。残る空白は、ハードウェアそのものの知識ではなく、「Windows の作法でそのハードウェアを駆動するカーネル側」が存在しないことにある。ここが本構想の新規性であり、同時に本丸である。

注意点も残る。Turnip の既存のカーネル接続は、Linux の MSM 系 Direct Rendering Manager ドライバや、Android の Kernel Graphics Support Layer（KGSL）を前提に設計されている。Windows 向けにそのまま載るわけではなく、カーネル境界の接続部は新規に設計する必要がある。これが後述する ioctl（入出力制御）表面の設計判断である。

## クリーンルーム手法

権利面の設計は、Nouveau や Asahi Linux が採った方式に倣い、観測、仕様書、実装の三つを分離する。

1. 観測する。自分のハードウェア上で、公開ドライバや公開知見を使い、振る舞いを記録する。
2. 仕様書に落とす。観測結果を、実装コードを含まない仕様として記述する。
3. 実装する。仕様書だけを根拠に、独立にコードを書く。

### 許容する情報源

- Mesa / freedreno の公開知見。rnndb のレジスタ定義、ir3 の命令セット、Turnip の公開コードと文書。
- Microsoft Windows Driver Kit（WDK）と Microsoft Learn の公開文書。WDDM のドライバモデル、必須の Device Driver Interface（DDI）、表示専用ドライバの位置づけはここで確認する。
- 自分のハードウェア上でのブラックボックス観測。レジスタ読み取り、コマンドのトレース、Event Tracing for Windows（ETW）、専用プローブによる計測。

### 避けること

- 逆コンパイル成果物のコード構造を複写しない。観測で得た「振る舞いと値」は仕様に書けるが、相手の実装の形を写さない。
- ファームウェア blob を配布物に含めない。前述のとおり、読み込むだけにする。
- 出所の分からないバイナリや、権利関係が不明な資料を土台にしない。

### 既にある観測基盤

この分離は、spacewar の本線作業で既に実践の形になっている。

- GX 系解析レポート群は、公式カーネルドライバ `qcdxkm` について、レジスタ値、書き込み列、Picture Parameter Set（PPS）やエンコーダ設定の照合結果を仕様として蓄積したものである。表示については、レジスタ設定の線が監査済みで閉じ、残りはフレーミングとタイミング側であるところまで仕様化が進んでいる。
- DscProbe は読み取り専用の計測ドライバであり、表示ブロックのレジスタを安全に採取する観測手段として既に動いている。

本構想の出発点は、この観測資産を「公開可能な仕様書」へ統合することである（マイルストーン M0）。

## アーキテクチャ

全体は、カーネルモードドライバ（Kernel-Mode Driver、KMD）とユーザーモードドライバ（User-Mode Driver、UMD）の二層に分ける。WDDM では、DirectX グラフィックスカーネルサブシステム（Dxgkrnl）が KMD の `DxgkDdi` 系関数を呼び、UMD がコマンドバッファを作り、KMD が検証してハードウェアへ投入する、という役割分担が公開文書で定義されている。

### KMD が本丸である

新規開発の中心は KMD である。担うべき仕事は次のとおりである。

- WDDM の `DxgkDdi` 表面。デバイス生成、アロケーション、コマンド提出、表示パス（Video Present Network、VidPN）まわりの必須関数群。
- System Memory Management Unit（SMMU）によるグラフィックスメモリ管理。アドレス変換、ページテーブル、アロケーションの配置と退避。
- Command Processor（CP）へのコマンドバッファのリング投入。
- 割り込みとフェンス。完了通知、タイムアウト検出、スケジューラとの連携。
- Graphics Management Unit（GMU）の起動と電源シーケンス。ファームウェア blob の読み込み、起動順序、スリープと復帰。
- Timeout Detection and Recovery（TDR）とハングリカバリ。失敗してもシステム全体を道連れにしないための復旧経路。
- 表示スキャンアウト。表示パイプライン（レイヤミキサ、ピンポンブロック、制御ブロック、DSC エンコーダ、インターフェースブロック）と Display Serial Interface（DSI）ホスト、パネル初期化。

KMD はカーネルで動くため、失敗は即ブルースクリーンにつながる。しかも ARM64 のスマートフォン文脈で WDDM の KMD を書いた公開実装は見当たらない。ここが規模とリスクの中心である。

### 表示は KMD のサブセットとして先行させる

WDDM には表示専用ドライバという区分があり、表示系の DDI を実装し、レンダリング系の DDI は返さない形が認められている（Microsoft Learn の WDDM ドライバ種別と機能 caps の表）。この区分を使えば、3D レンダリングを持たない表示だけの KMD を最初の到達点にできる。

これは本線の表示ラダーの最終段「表示専用ドライバ」と一致する。本線側では「バイナリドライバでは触れない箇所と判明した場合のみ」という最後の手段だが、本構想ではそれがそのままマイルストーン M1 になる。オペレーティングシステムがソフトウェア描画した画面を表示パイプラインへ流すだけでも、「グラフィックス処理装置経由で正しく描画できた」という最初の事実が得られる。

### UMD は Turnip を再利用し、接続部だけを新規に設計する

UMD 側で Vulkan を一から書く理由はない。Turnip と ir3 を再利用し、新規に書くのは Turnip と自作 KMD のあいだのカーネル接続（Turnip 側では knl と呼ばれる抽象層）である。

その接続表面の設計には二案あり、どちらを選ぶかは本構想の主要な未決事項である。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 案 A：互換寄せ | Qualcomm KMD 互換に近い ioctl 表面を用意し、既存の Turnip の Windows / WDDM 系資産に寄せる | 既存資産を活かしやすく、最初の描画までの距離が短い可能性がある | 互換対象の表面そのものが未公開であり、その仕様化が権利面と保守面の両方で重い。相手の変更や癖に引きずられる |
| 案 B：独自定義 | クリーンな独自 ioctl を定義し、Turnip 側に新しい knl バックエンドを足す | 表面を自分で説明でき、仕様書と実装が一致する。権利面で最もきれいな形になる | Turnip 側への追加実装と、その上流との乖離を抱える。保守は自前になる |

権利面と保守面では案 B が素直であり、初期速度では案 A が有利な可能性がある。ただし案 A の「既存資産がどこまで実在し、どこまで使えるか」は未検証であり、速度の見積もりを案 A 前提で固定しない。M0 の仕様統合の段階で、Turnip 側の接続抽象が何を要求するかを先に確定させ、それを判断材料にする。

なお Direct3D については、DXVK が Direct3D 8/9/10/11 の呼び出しを Vulkan へ変換する公開の変換層であるため、Vulkan が動けばその上に載せられる。Direct3D 12 は DXVK の対象外であり、本構想でも初期対象にしない。

### プラットフォームへのバインドと電源モデル

- デバイスのバインドは Advanced Configuration and Power Interface（ACPI）側の識別子に寄せ、INF では `VEN_QCOM&DEV_0A36` を対象にする想定である。実際の識別子と一致するかは、配備時に実機のデバイスツリーで確認する前提であり、ここでは想定として置く。
- 署名は当面テスト署名で運用する。本線と同じく、テスト署名環境でのみ読み込まれる前提を明記し、正式署名や配布形態は未決事項に残す。
- 電源は Platform Extension Plug-in（PEP）の電源モデルと相互作用する。本線の教訓として、電源レールをモデルの外から直接叩く方法は危険であり、グラフィックスの電源要求も PEP のデバイス電源モデルに沿った形で設計する必要がある。タッチ電源で得た「モデルに登録されていない要求は、他のデバイスの起動時の再計算で落とされる」という知見は、ここでも同じ形で効く。

## マイルストーン

順序は「観測できている範囲から、動く範囲を広げる」原則で置く。各段の完了条件は、見た目の印象ではなく、読み戻しや再現性で確認できる形にする。

| 段 | 内容 | 完了の目安 |
|---|---|---|
| M0 | 仕様の統合。GX 系の蓄積とプローブ観測を、公開可能な仕様書へまとめる | レジスタ、起動順序、電源順序、表示パイプラインについて、観測根拠のある仕様が文書として揃う |
| M1 | 表示専用 KMD | グラフィックス処理装置経由で少しでも正常に描画できる。単色、テストパターン、フレームバッファ表示のいずれかが、安定して正しく出る |
| M2 | 最小レンダリング | 画面クリアと三角形が、Turnip 経由で描ける |
| M3 | 実アプリの煙試験 | DXVK 経由で実アプリまたはゲームが起動し、描画が崩れない |
| M4 | 堅牢化 | TDR、サスペンドとレジューム、複数コンテキストが扱える |

M1 の位置づけは重要である。本線で目指している「GPU を使用して少しでも正常に描画してみたい」という最初のゴールと、本構想の M1 は同じ到達点である。テストパターン生成による切り分けや、DSC オフによる無圧縮表示の実験は、どちらの線でも M1 の前提実験になる。

### 下支えになる依存：0x101 凍結と GX74

spacewar では、グラフィックス有効化の前後で 2 つのプロセッサが相互ランデブーに入り、完了しない BugCheck 0x101 の凍結が起きる。相手側は任意のシステム活動であり、ドライバ自身の直列化では防げないことが分かっている。

自作 KMD でも、グラフィックス起動が同じ種類の相互作用を引き起こす可能性は残る。そのため、各プロセッサが自分の状態を自前で記録する計測（GX74）が下支えになる。GX74 は表示やフレーミングを直すものではなく、停止が「配送、受理、処理」のどの層かを見分けるための計測であり、その決着は本構想の電源と起動シーケンス設計にも効く。

## リスクと未決事項

未決事項を先に並べる。これらが決まるまでは、実装計画ではなく構想である。

- WDDM のバージョン選定。対象は Windows 11 22H2 の ARM64 であり、どの WDDM バージョンとどの DDI セットを最小要件にするかで、KMD の表面積が大きく変わる。
- スケジューラのモデル。オペレーティングシステム側のスケジューリングにどこまで寄せるか、ハードウェアキューをどう見せるか。
- SMMU の使い方。アドレス空間の分け方、コンテキストとの対応、表示スキャンアウトとの共有方法。
- GMU ファームウェアとのインターフェースの安定性。blob の版が変わったときに、起動シーケンスとメッセージ形式がどこまで保たれるか。
- PEP 電源モデルとの整合。電源要求の登録方法、他のサブシステムとの競合の避け方。
- 署名と配布形態。テスト署名のままにするのか、配布可能な署名を目指すのか。ファームウェア blob を含めない配布物の形。
- ioctl 表面の選択。前述の案 A と案 B のどちらを採るか。

リスクとして正直に置くべき点は三つある。第一に、KMD の失敗はブルースクリーンであり、実験のたびに復旧コストがかかる。第二に、ファームウェア blob は署名済みであり差し替えられないため、そのインターフェースが不安定なら設計ごと影響を受ける。第三に、パネル側の仕様は公開資料が乏しく、表示部分は実機実験で決める範囲が残る。

### 規模感

個人から小規模の体制で、年単位の仕事である。表示だけでも月単位というのが、本線側で表示専用ドライバを見積もったときの感触である。

ただしコールドスタートではない。シェーダコンパイラ ir3 と Vulkan の UMD（Turnip）が既存であり、レジスタと命令セットの知見も公開されている。新規に書くべきものは KMD とその接続部に集中している。その集中が、この構想を「全部を一から作る話」から「空白地帯がひとつに絞られた話」に変えている。

## 本線との関係

本構想は本線の代替ではない。関係は次のように整理する。

- 観測資産は双方向に共有される。DscProbe によるレジスタ採取、GX 系レポートの仕様化、メインライン側の実値採取は、本線の切り分けにも本構想の M0 にも使える。
- DSC オフ実装は、本線では圧縮まわりとそれ以外を二分する実験であり、本構想では無圧縮表示という M1 の前提実験になる。同じ実験が両方に効く。
- 表示ラダーの知見（レジスタ設定は閉じ、残りはフレーミング、順序、タイミングと DSI エラー領域である、という整理）は、M1 で表示パイプラインを新規に書く際の設計入力になる。逆に、M1 の実装で詰まった箇所が本線のブラックボックスと共通の土台であれば、それ自体が本線への情報になる。
- 本線の安全規則は本構想の実験にもそのまま適用する。グラフィックスはブート時に無効を既定とし、有効化は静かな条件で短く行い、実験後は無効化と ConfigFlags の確認までをひと続きとする。
